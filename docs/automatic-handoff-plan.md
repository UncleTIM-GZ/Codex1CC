# Codex1CC 自动接管执行计划

状态：A0–A4 已完成实验实现；A5 的模拟端到端和一次真实 CC → Codex 自动验收已通过。真实问题交接、宿主运行中重启恢复及跨机器兼容性仍待验收。本文件记录 v1.2 自动接管范围；v1.3 写入能力见[写入后端计划](native-write-backend-plan.md)。依据：[当前 PRD](../Codex1CC%20产品需求文档.md)第 14 节。实测边界见[兼容性记录](handoff-compatibility.md)和[验证记录](validation.md)。

## 1. 交付目标

用户在 Codex 中派出完整任务后，无需追问；CC 交付、请求回答或异常时，程序触发指定 Codex 会话处理并展示结论。普通进度由程序保存和显示，等待期间没有模型查询调用。

继续沿用完整委托、共享上下文文件、默认只交结论和同项目单任务约束。此计划不开放编辑权限，不自动提交或推送用户项目，不改变尚未验证的平台隔离边界。

## 2. 基线与实施顺序

已有基础：`daemon.py` 接收 CC 流式事件并管理任务状态；`store.py` 持久化任务与事件；七个 MCP 工具支持查询、回答、续接和验收。当前没有宿主绑定、主动投递及处理回执。

按 A0 → A1 → A2 → A3 → A4 → A5 执行。宿主实验、事件契约、投递与验收前后依赖，作为一条连贯工作推进，不拆成多个 Agent。只有契约稳定后，互不修改相同文件的独立文档或平台验证才可考虑并行。

## A0：验证 Codex 接管接口

**工作：**

- 使用非敏感临时项目和专用测试会话，核对已安装 Codex 版本及接口能力。
- 首先验证 App Server：指定会话、启动一轮、获得 turn_id、接收完成事件及读取最终输出。
- 验证能否接入用户原会话，以及空闲、忙碌、窗口关闭、断线后的准确行为；不能接入时验证由产品管理的专用会话和结果入口。
- `codex queue` 作为候选方案，只有确认会自动处理、可关联回执并具备可靠去重或对账机制后才采用。禁止通过模拟键盘输入实现投递。
- 记录认证、用户审批、上下文与权限继承方式；不能为接管绕过原审批策略。

**交付：** `docs/handoff-compatibility.md`，记录平台、版本、连接方式、支持场景、失败表现和可复现步骤；确定一个首发适配器。

**通过条件：** 不依赖用户发送第二条消息，事件触发指定会话产生可见结果，并可关联启动与完成记录。仅确认命令存在或消息进入队列不算通过。此门槛不通过时，不进入宣称支持自动接管的实现；记录具体限制。

## A1：持久化事件与迁移

**涉及：** `src/codex1cc/store.py`、新增迁移及测试。

**工作：**

- 定义宿主绑定、处理策略、待投递事件与处理记录的数据结构。
- 在同一事务中更新任务状态并追加待投递事件；为问题、轮次及状态版本建立稳定唯一键。
- 保存 pending/accepted/handled、投递次数、错误、下一次重试时间、关联 turn_id 和处理结论。
- 为处理中的事件建立可恢复的消费占用机制；取消和状态变化让旧事件失效，保留审计依据。
- 兼容已有数据库与任务；旧任务不自动绑定会话或集中触发模型。备份数据库后迁移，定义旧版本不兼容时的恢复方法。

**通过条件：** 事务故障注入不丢事件；重复写入只有一个逻辑事件；旧库升级保留原任务；未处理事件不被保留期清理。

## A2：程序监听、投递与宿主适配器

**涉及：** `daemon.py`、新建投递模块及 A0 确定的宿主适配器。

**工作：**

- 从状态变化、内部提问、进程退出及超时处理直接生成事件；普通日志只写入已有事件记录。
- 使用异步等待和宿主事件流调度；不增加模型监控循环或周期性 list_tasks/get_task。
- 同会话串行投递；空闲时启动处理，忙碌时排队，完成事件驱动下一次处理。
- 实现有上限的传输退避、断线重连及启动时补送。对已启动但回执缺失的调用按 turn_id 对账；无法判定时暂停该事件并显示待核对。
- 限定当前用户注册的宿主地址和会话；使用结构化参数，不拼接 Shell，不把 CC 输出作为控制指令。

**通过条件：** 模拟长任务无监控模型调用；重复投递、断线和重启不重复触发业务动作；故障恢复后事件可接手，取消后不再自动续接。

## A3：Codex 验收与回答闭环

**涉及：** `mcp_server.py`、`daemon.py`、接管指令模板及处理回执接口。

**工作：**

- 扩展 submit_task，支持已注册绑定与接管策略，返回 connected/degraded/disabled 及原因。自动模式预检失败不创建任务；手动模式保留兼容。
- get_task/list_tasks 返回有界的接管状态、待处理原因和最后活动时间。
- 接管输入仅包含事件类型、任务与轮次标识及有界摘要；公共信息仍引用共享文件，完整证据按需读取。
- Codex 处理前核对任务当前状态及原验收要求，选择回答、验收完成、原任务续接、排查或请求用户决定。
- 增加结构化处理回执，关联 event_id、turn_id、结果及相关动作；“已读”和“模型回合结束”均不能单独冒充已处理。
- 通过稳定 request_id、事件消费记录及状态校验共同保证动作幂等。
- 单独约束 Codex 接管次数、时间和可核实费用；未知费用如实显示。不得自动扩大 CC 的范围和预算。

**通过条件：** 完成、问题、失败三种事件均跑通；过期问题、重复事件和用户中途取消不会触发错误动作；超预算或需要用户决定时明确等待用户。

## A4：初始化、进度显示与操作说明

**涉及：** `cli.py`、配置模块、进度入口、中英文 README。

**工作：**

- 增加初始化绑定和停用入口，具体命令名称在 A0 接口确定后固化；安装不覆盖用户现有 MCP 或 Codex 配置。
- doctor 区分静态依赖检查与主动端到端验证。真实模型验证显式启动，并显示可能产生费用；普通 doctor 不自动消耗模型额度。
- 提供程序驱动的进度流入口，显示最后活动时间、任务状态、连接状态、待处理事件与最终结论；不调用模型整理每条进度。
- 说明窗口关闭、后台服务停止、主机休眠、离线及重连后的实际行为；服务无法运行时不承诺即时接管。
- 在中英文 README 中同步初始化、自然语言用法、进度查看、故障恢复、停用和预算说明；公开样例统一使用 demo，不包含开发者机器信息。

**通过条件：** 新用户依据文档能完成绑定、派单、看到自动结论和停用；不支持的宿主显示可操作原因；AI 可根据结构化状态判断下一步。

## A5：端到端验收与发布

先用模拟执行器和宿主故障注入完成下表，再在 A0 选定的受支持组合做少量非敏感真实任务。记录模型调用次数、事件编号、回执、结果位置和费用是否已知，不公开凭据或个人路径。

| 场景 | 必须观察到的结果 |
|---|---|
| 用户派单后不再输入 | CC 完成 → Codex 自动验收 → 用户可见结论 |
| CC 请求回答 | 自动回答已有依据的问题，原轮次继续；需用户决定时显示问题 |
| CC 异常或达到上限 | 自动接手并说明原因，不重交原任务 |
| 长时间持续输出日志 | 日志可查看；等待期模型查询和定时工具查询次数为零 |
| Codex 忙碌 | 事件持久排队，空闲后处理 |
| 断线、重启、发送前后崩溃 | 恢复后补送；结果不确定时先对账 |
| 重复事件、处理后回执丢失 | 无重复回答、续接或完成操作 |
| 排队期间取消或问题过期 | 旧事件失效，不执行旧动作 |
| 超过接管次数或预算 | 停止自动模型调用并明确显示原因 |
| 原窗口关闭或宿主不支持 | 与兼容性矩阵一致，不虚报已接管 |
| 旧配置、旧数据库和手动模式 | 原流程可使用，旧任务不自动产生模型费用 |

**交付：** 更新 `docs/validation.md`、兼容性矩阵、中英文使用说明和发布说明；区分模拟验证、真实验证和未支持能力。

**发布门槛：** 至少一个明确版本与平台组合通过全部自动接管场景；其他组合按测试证据列为未验证或不支持。现有 macOS 隔离等门槛独立保留，自动接管测试不能代替项目文件隔离测试。

## 3. 完成定义与停止条件

完成定义：自动接管代码、迁移、测试、初始化、进度与结果入口、中英文说明均交付，并在明确支持的组合上证明“只派一次，无需追问，无模型轮询，自动验收”。

若宿主没有可靠触发接口、模型调用结果无法关联或重复消费无法防止，先修复该具体缺口；不得用高频查询、无限重试或要求用户反复粘贴提示词替代。运行时达到权限或预算边界则保留记录并等待用户决定。

当前实现：`handoff_host.py`、持久待投递事件、程序监听与回执、`bind`/`unbind`/`watch`、MCP 自动模式及相关测试已落地。一次真实 CC → Codex 自动验收通过；真实问题交接、宿主重启中途恢复、跨平台发布门槛仍需后续验收；未验证项不得宣称通过。
