# 显式多 Agent 并行执行计划（PRD v1.5）

## 目标与准入原则

Codex 对每个连贯目标仍一次派清。只有目标之间没有语义或产物依赖、文件范围互不重叠，才让同项目多个 CC 任务同时运行。每项任务持有独立 CC 进程、会话、预算、事件；写入任务另有独立分支和 Git worktree。工作树隔离可减少代码和上下文相互污染，但不构成命令级文件或网络沙箱。

项目配置 `parallel.max_agents` 为 1–4，默认 3；`submit_task.parallel_ok` 默认 false。若已有活跃任务，新任务和所有活跃任务都须明确声明可并行，数量未到上限，且所有 `scope` 无相同路径、父子目录或 `"."` 全仓覆盖冲突。Codex 负责判断路径检查无法识别的语义依赖和共享运行环境。任何条件不满足，执行器返回 `PROJECT_BUSY`，不创建后台队列。

## 实施步骤

1. **配置和接口。** 校验并保存项目并行上限、任务并行声明。未设置上限的项目采用 3；旧任务默认不可并行，未显式声明的后续任务也保持串行准入。MCP 输入、提交摘要和文档说明默认值与 `PROJECT_BUSY` 的含义。
2. **原子准入。** 在任务创建时对同项目 `queued`、`running`、`waiting_answer`、`continuing` 状态计数和核对范围。准入与记录必须在执行器的串行事务边界内，避免两个同时提交都认为尚有名额。重复 `request_id` 返回原任务，不创建第二进程或工作树。
3. **任务隔离。** 每任务启动独立 CC CLI 进程并分别保存会话 ID、进程归属、用量、事件和退出原因。写入任务在提交时独立创建 `codex1cc/<task_id>` 分支及 worktree；取消、超时与失败只停止自身进程，保留自身现场。流式进度不触发 Codex 模型轮询；提问、交付和失败仍通过原有事件接管。
4. **基线和串行后继。** 每项写入任务记录 `base_commit`，从项目根工作树当时的 `HEAD` 启动。Codex 提交前核对项目 `HEAD`，提交后核对返回的 `base_commit`；需要先前任务产物的后继任务必须等待前序交付与验收，将接受的提交按项目流程整合进正确的基线，然后再新建任务。后继不能从旧 `HEAD`、仅停在前序独立 worktree 的提交，或未经验收的结果开始。`PROJECT_BUSY` 后不自动重交，等待相关任务的交付事件再由 Codex 决定。
5. **验证与发布说明。** 完成下述自动和真实验收后，在 README 与 skill 中提供配置、拆分判断、冲突处理及基线核对示例。未验证的平台和场景如实标明。

## 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 默认配置，两个同项目任务均未声明 `parallel_ok` | 第二项 `PROJECT_BUSY`；旧用法不变 |
| 默认配置，三项独立且均声明 `parallel_ok=true` | 最多三项同时运行；第四项返回 `PROJECT_BUSY` |
| 上限 2，两项独立且范围不重叠，双方 `parallel_ok=true` | 两项同时运行，进程、会话、工作树、事件与预算互不混用 |
| 同路径、目录父子关系或任一 `scope=["."]` | 第二项 `PROJECT_BUSY`；无遗留新任务或 worktree |
| 任一任务未声明可并行，或达到项目上限 | 第二项 `PROJECT_BUSY`；不在后台排队 |
| 同时提交、重复 `request_id`、daemon 重启 | 不超配额、不重复创建、状态和事件可恢复 |
| 取消或失败其中一项 | 只影响该任务；另一个任务继续，失败现场保留 |
| 两个独立任务交付后启动依赖前序结果的任务 | Codex 验收并整合前序提交后，新任务 `base_commit` 为正确基线 |
| 非敏感真实临时 Git 项目 | 观察到两个真实 CC 进程/会话/worktree 并行，分别交付可审查产物；串行后继基线正确 |

自动测试只证明程序准入与隔离。真实模型、不同操作系统、宿主接管和外部共享资源行为需分别验收。并行会增加同时发生的模型调用和费用；每任务原有时间、费用、上下文压缩和错误分类独立生效，项目上限只限制活跃任务数量。

## 安全边界与未实现项

`scope`、`write_paths` 和 worktree 提供声明、Git 工作文件隔离与交付后审查，不能阻止受信任写入模式中的 CC 命令读取其他本机路径、访问网络或操作共享服务。语义依赖、共享测试环境和最终合并冲突需要 Codex 判断；路径不重叠不代表安全并行。

本阶段不提供 Claude 单任务内部子代理、自动拆任务、自动语义冲突识别、冲突任务队列、依赖图调度、自动合并/变基/推送、自动继承其他任务的提交，也不对原生 CC 后台作业进行接管。只有在各项验收完成后，才能把并行能力从实验性提升为已验证。
